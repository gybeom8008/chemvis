# 단계 1 접촉 판정기

기준은 [합의 문서](lab-decisions.md), [자료 행 3판](lab-rows-stage1.md), [설계서 4절](lab-astra.md#4-반응-판정-두-입자만-보는-함수로는-부족하다)이다. 합의와 3판에서 바꾼 범위가 이전 설계보다 우선한다. 이 문서는 순수 판정 모듈과 화면 연결 계약을 설명한다. 화면, 실행 취소, 대본 생성기와 엔진 실행은 구현하지 않았다.

## 파일과 자료

| 파일 | 맡은 일 |
|---|---|
| `src/lab/stage1-data.ts` | 재료 15종, V01–V08, S01–S08, C01–C15, 사건 8개, 부정 인증 13개, T001–T120을 보관한다 |
| `src/lab/judge.ts` | 접촉 후보를 찾고 무대 맥락·경쟁·필요량을 검사한다. 한 사건에 필요한 실제 원자 ID와 예상 생성물을 계획한다 |
| `tests/unit/lab-judge.test.ts` | 문서와 코드 자료, 양방향 120쌍, 조건·맥락·예약, 원본 대본 컴파일을 검사한다 |

자료 모듈은 문서 파일을 실행 중에 읽지 않는다. 각 표 행의 `documentCells`에는 셀 내용을 그대로 보관한다. 이름·수치·이유·문구를 바꾸면 원문 대조 검사도 실패하도록 했다. 사건의 단계 대본은 문서에 있는 독립 fixture 그대로이며, 현재 무대에서 곧바로 실행할 대본이 아니다. 실제 원자 ID와 별칭을 연결하는 일은 별도다.

각 행은 `conditions`와 `review`를 갖는다. 조건은 `water / 25 / ordinary / none`, 자유 용질 활동도 참고 구간은 `[0.001, 0.01]`이다. 자료 버전은 `stage1-v3-draft-2026-11-12`이다. 모든 행은 여전히 `draft`, 검토자는 `null`이다. `authorReadingNote`는 문서 작성 당시 원문 열람 기록을 옮긴 필드이며, 이번 구현에서 외부 원문을 다시 읽었다는 뜻이 아니다. 승인과 출처 화면은 Claude가 실제 대조 기록에 맞춰 연결해야 한다.

`engineFormula`는 그래프 생성에 쓸 엔진 화학식이다. `graphKind`가 `component`이면 분자·자유 이온, `ionic-crystal`이면 이온 결정, `metal`이면 금속 조각으로 만든다. AgCl·NaCl을 공유 결합 분자로 만들지 않는다. 재료의 `atomCount`와 `modelElectrons`는 한 재고 단위 값이다. 금속 한 단위는 원자 하나이고, 최초 조각에는 이런 원자 여섯 개가 있다. 전자는 엔진에서 표시하는 장부만 세며 원자 전체 전자 수를 뜻하지 않는다.

`deriveStage1Numbers()`는 V행으로 C01–C15를 다시 계산한다. 전위 구간에는 C08의 계산용 `0.05916 V`를 쓰고, logK에는 반올림 전 계수를 써서 문서의 표기값을 재현한다. 원문 표시 문자열은 별도로 유지한다. D01에 Ksp나 포화 농도를 새로 만들지 않는다. 화면 입자 수는 계산 입력이 아니다.

## 입력 계약

`MaterialRef`는 현재 그래프를 대조한 연결 계층이 만든다. 판정기가 엔진의 `World`를 읽거나 분자식을 보고 구조를 알아내지는 않는다.

| 필드 | 계약 |
|---|---|
| `instanceId`, `revision` | 지금 잡을 수 있는 재고 단위와 무대 버전이다. 요약을 만들 때 모든 손잡이에 현재 무대 버전을 찍는다 |
| `speciesId`, `phase`, `charge` | 현재 종·상·총전하다. 생성 당시 이름이나 `owner`로 정하지 않는다 |
| `structure` | 현재 원소·결합·전자·상·소속을 대조한 경우에만 `matched`이다. 읽을 수 있지만 미검토이면 `unreviewed`, 끊긴 참조 등 잘못된 구조이면 `invalid`이다 |
| `atomIds`, `anchorAtomId` | 한 분자 전체, 자유 이온 하나, 결정 한 화학식 단위, 또는 금속 원자 하나다. 기준 원자는 O·N·금속 원자이며 결정 단위는 양이온이다 |
| `transferableHydrogenIds` | 현재 산의 기준 O·N에 결합한 H 목록이다. 다른 분자에서 온 H도 실제 ID로 넣는다 |
| `selectedHydrogenId` | 사용자가 고른 동등한 H다. 없으면 안정 ID 순으로 고른다. 거리로 고를 화면은 가장 가까운 H를 이 필드에 넣는다 |
| `aggregateId`, `surface` | 고체 재고의 소속과 검토된 상태다. 자유 이온에는 소속을 넣지 않는다. 접촉 중인 양이온을 중성 금속으로 등록하지 않는다 |
| `location` | `active`, `shelf`, `background`다. 선반은 맥락·예약에서 제외하고 배경 물은 재료로 예약하지 않는다 |
| `available`, `distancePx` | 다른 계획에서 예약했으면 `available: false`다. 추가 Ag⁺는 CSS px 거리 120 이하에서만 예약한다. 거리 미지정은 자동 예약하지 않는다 |

판정기는 원자 수·중복·기준 원자·수소 목록·상·전하·소속의 기본 일관성을 확인한다. 그러나 `structure: 'matched'`라는 표시는 신뢰 경계다. 실제 원소와 결합을 확인하지 않고 이 값을 붙이면 안 된다. 임의 SMILES에 등록 종 ID만 붙여 넘기는 것도 금지한다. 원소별 보존과 실제 전자 장부는 엔진 연결 단계에서 다시 확인한다.

`SceneSummary.particles`에는 자유 분자·이온과 필요한 배경 물 손잡이를 넣고, 고체 재고는 `aggregates[].members`에만 넣는다. 같은 원자나 인스턴스를 두 곳에 넣으면 조작 오류다. 몸체에 남은 원자까지 모두 넣어야 한다. R01 뒤 아연 다섯 개와 생성 구리는 같은 조각의 구성원 여섯 개로 요약한다. 선택한 구리만 보내면 판정기가 누락된 아연을 알아낼 수 없다.

빈 결정은 `members: []`로 남겨도 활성 맥락이나 onto 후보로 세지 않는다. 조각 위치와 구성원 위치는 같아야 한다. 선반으로 옮길 때 구성원도 함께 옮긴다. `backgroundEffects`에는 명시된 피막·외부 효과 등 미지원 조건을 넣으며, 하나라도 있으면 양성·부정 맥락을 승인하지 않는다. `freeBackgroundWaterCount`는 금속 이탈 후 수화에 쓸 자유 배경 물 재고다. 선택 물 분자는 이 수를 대신하지 않는다.

## 두 함수의 반환값

```ts
classifyContact(a: MaterialRef, b: MaterialRef, env: Environment): ContactResult
planEvent(candidate: ContactResult, scene: SceneSummary): PlannedResult
```

두 함수 모두 입력과 무대를 바꾸지 않는다. 첫 함수는 입력을 복사해 후보에 붙인다. 두 번째 함수는 현재 손잡이·무대 버전·조건을 대조하고 현재 자료로 다시 판정한다. 전달된 `eventId`만 믿고 실행 계획을 만들지 않는다. 이전 버전 후보는 폐기하고 다시 계산한다.

| `kind` | 뜻과 다음 처리 |
|---|---|
| `reacts`, `needs-scene` | 두 재료의 조건부 양성이다. 아직 최종 결과가 아니므로 반드시 `planEvent`를 호출한다 |
| `reacts`, `needs-material` | 반응 방향은 등록되어 있으나 한 사건에 쓸 재료가 부족하다. `missing`에 종·개수·가져올 재고 ID·문구가 있다 |
| `reacts`, `preflight` | 맥락과 재고 예약 계획을 만들었다. 실제 컴파일과 끝 상태 대조가 남았다 |
| `no-reaction` | 명시된 인증 범위만 부정한다. 제목·자세히·인증 ID를 돌려준다. 첫 함수에서 받은 부정도 무대 맥락 검사가 필요하다 |
| `unknown` | 사유 코드, 네 묶음 중 한 제목, 자세히 문구를 돌려준다. 생성물 계획은 없다 |
| `execution-failure` | `RULE_CONFLICT` 또는 `REPRESENTATION_UNAVAILABLE`이다. “장면을 정확히 만들지 못했어요.”로 표시하며 화학적 모름이나 부정으로 바꾸지 않는다 |
| `input-error` | 같은 대상, 잘못된 참조, 오래된 후보, 사용할 수 없는 대상이다. 화학 결과 카드로 표시하지 않는다 |

`preflight`는 실행 가능 판정인 `ready`가 아니다. 모든 계획에는 `canExecute: false`와 실제 `review`가 있다. 자료 승인, 실제 그래프 검사와 임시 컴파일을 생략해 재생하는 일을 막기 위한 경계다. 현재 단계에서 `draft` 자료로 내부 후보와 계획을 검사할 수는 있지만 이를 공개 실행 승인으로 해석하지 않는다.

모름의 제목은 자료 3판에서 합의 문서 3절과 F1을 반영한 네 문장을 그대로 쓴다. 모든 자세히 문구는 합의된 공통 두 문장으로 시작한다. 사건의 과거형 결과 제목은 실제 적용에 성공한 뒤 표시한다. 재료 부족 중에는 `missing[].message`가 먼저 보이게 한다.

## 판정과 예약 순서

1. 참조·버전·서로 다른 대상인지 확인한다. 다음으로 환경을 확인한다. 기본 환경이 지원 밖이면 `ENV_UNSUPPORTED`, 값이 없거나 미지정이면 `CONDITION_MISSING`이다. `veryDilute`도 단계 1에서는 지원하지 않는다.
2. 물속 중성 HCl 경계는 `SPECIATION_UNSUPPORTED`, 일반 미검토 구조는 `SPECIES_UNREVIEWED`이다. 종·상의 쌍으로 T행을 찾고 반응 자리를 검사한다. 수치 방향은 고정 참고 구간에서만 확인한다.
3. 양성·부정 후보에 활성 무대 전체를 적용한다. 부정 인증은 해당 두 종과 물만 허용한다. 양성은 3판 6.1절의 목록을 사용한다. 단순히 양이온이라는 이유로 관찰자라고 추정하지 않는다.
4. R01의 Ag⁺, R02의 Cu²⁺·Cu(s), R03의 Zn(s)는 `COMPETING_PATHWAYS`다. 조각 안의 구성원도 포함한다. 그 밖의 허용 목록 밖 재료는 `CONTEXT_UNREVIEWED`다. 경쟁과 맥락 검사는 부족 재료보다 먼저다.
5. 접촉한 재고를 우선 예약한다. 추가 Ag⁺는 사용할 수 있고 가까운 것부터, 거리 동률이면 기준 AtomId 순으로 하나만 고른다. 한 조작으로 반응을 반복하지 않는다. 물 손잡이는 `consumed: false`다.
6. 필요한 엔진 기능과 금속 수화용 배경 물을 확인한다. P01의 onto는 명시한 활성 순수 AgCl을 우선한다. 명시하지 않았으면 같은 고체 중 가까운 것, 동률 또는 거리 미지정이면 안정 고체 ID 순으로 고른다. 없는 대상·빈 대상은 표현 실패다. 다른 염·금속이 활성 무대에 있으면 앞선 맥락 검사에서 이미 차단될 수 있다.
7. `reservations`, `atomRoles`, `expectedProducts`, `unchangedAtomIds`를 만든다. 이동 H를 포함한 실제 원자 ID를 유지하고, 재고 자료를 기준으로 원자 집합·개수·전하·모형 전자 합을 대조한다. 새 침전 이름은 추측하지 않고 비워 둔다. 이 계획을 엔진에서 검증하는 일은 다음 단계다.

`expectedProducts`는 반응에 낀 재고만 다룬다. 물 손잡이, 남은 금속 몸체, 관찰자는 `unchangedAtomIds`에 있다. 고체가 커지거나 줄어도 이 원자들의 ID·전자·상태를 임의로 바꾸면 안 된다. 배경 수화 물은 별도 연출 재고다.

## Claude가 연결할 일

1. 현재 `World`에서 구조를 대조해 위 요약을 만든다. `owner`는 처음 이름일 뿐이다. 소속만으로 금속을 판별하지 않고 원소·전하·`lattice`·현재 그래프를 함께 확인한다. 이온 결정에는 금속용 `lattice=true`를 요구하지 않는다.
2. 드롭할 때 `classifyContact`와 `planEvent`를 호출한다. 서로 다른 접촉 후보가 여럿이면 화면에서 선택하게 한다. 동등한 수소 선택과 포인터 거리 판단도 화면에서 처리한다. 반응 계열에 임의 우선순위를 주지 않는다.
3. `preflight` 계획의 예약 원자에 별칭을 붙여 해당 사건 템플릿을 치환한다. `atomRoles.hydrogen`은 `a.H1`일 수도 있고 다른 분자에서 온 ID일 수도 있다. `owner`로 수소 이름을 재작성하지 않는다. R 사건은 세 step을 한 `compileFrom` 호출로 묶는다.
4. `compileFrom`으로 임시 컴파일한 뒤 계획과 실제 끝 상태를 대조한다. 원소별 수, 정확한 원자 매핑, 결합, 전자 장부, 전하, 생성물 그래프·상·소속, 관찰자 상태·좌표를 확인한다. 누락된 H나 계획과 다른 H 이동을 컴파일 성공만으로 통과시키지 않는다. 검토 기록과 필요한 화면 표현도 확인한다.
5. 실패하면 부분 결과를 적용하지 않는다. 성공해도 적용 직전에 revision과 예약 ID를 다시 확인한다. 사건 한 번만 확정하고, 재생 중 중간 Zn⁺·Cu⁺를 새 재료로 노출하지 않는다. 새 결정 ID는 effects에서 받고, 빈 결정은 활성 목록에서 제외한다.
6. 실행 취소·다시 실행에는 World, 상·인스턴스·고체 구성원·선반·예약·이름 발급 상태를 함께 저장한다. revision은 되돌리지 않는다. 다시 보기는 화학 상태를 다시 적용하는 조작이 아니다.

## 검사 범위와 남은 검토

120개 쌍은 테스트에서 문서 표를 직접 읽어 기대 판정과 코드를 얻는다. 코드의 자료 배열을 기대값으로 되돌려 쓰지 않는다. 양방향 모두 검사하며 양성 8·부정 13·모름 99와 중복·누락을 확인한다. 모든 사건에서 15종 각각을 추가해 허용 목록과 경쟁 차단을 검사하고, 모든 부정 인증에서도 같은 범위 검사를 한다.

| 설계서 10절 사례 | 이 단계의 처리 |
|---|---|
| T01·T02·T05·T07·T09·T13–T20 | 단계 1 양성, 역순, H 선택, 재고 부족, 한 사건 예약, 선택 Ag⁺를 검사한다 |
| T21·T27·T29·T32·T35–T37 | 3판의 해당 인증과 좁아진 맥락으로 검사한다 |
| T42·T43·T45·T47–T58·T60 | 해당 T행 또는 외부 입력 경계로 검사한다 |
| T59 | Br⁻는 단계 1 미등록이므로 3판 P01 허용 목록에 따라 `CONTEXT_UNREVIEWED`다. 단계 2의 두 은염 경쟁으로 확대하지 않는다 |

나머지 산·염기, K⁺·Br⁻ 재료와 `veryDilute` 부정 인증은 단계 1 밖이다. 여덟 사건 템플릿이 `compileFrom`으로 컴파일되고 base를 보존하는지 별도로 검사한다. 재료 화학식 15개도 상에 맞게 생성해 원자 수·전하·모형 전자 수를 비교한다. 자세한 엔진 끝 상태 검사는 기존 `lab-rows.test.ts`가 맡는다. 이 검사들을 원자 궤적·각진 판·전자 점·화면 연결의 인수 완료로 해석하지 않는다.

Claude는 특히 `draft` 자료 공개 승인, 구조 대조에서 요약으로 넘어가는 신뢰 경계, 금속 몸체 전체 재고, 고체 한 단위의 양이온 기준 원자, 현재 H ID 치환, E5 검사와 적용 직전 revision 재확인을 검토해야 한다. 외부 원문 재대조와 UI 시각 검증은 이번 구현에서 수행하지 않았다.
